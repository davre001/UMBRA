# Known Limitations & Simplifications

This document plainly states what is explicitly not handled, interim simplifications, and current boundaries in the UMBRA protocol. Reviewers and contributors can check these known gaps against current implementations.

---

## 1. Bitcoin SPV Checkpoint: Genesis Trust + No Fork-Choice (v1 Permissionless Relay)

- **Limitation**: The `btc_deposit` Noir circuit proves that a transaction was included in a block whose header is an ancestor of an on-chain checkpoint header. As of the timelock/checkpoint-relay redesign, `ShieldedVault.checkpoints[sourceChainId]` is no longer an admin-writable value after its one-time genesis: `executeInitializeCheckpoint` (timelocked, write-once) registers a real, deeply-buried signet block an operator picks as the trust anchor, and every advance after that must be a permissionless `extendCheckpoint` call carrying a real Noir proof (`circuits/noir/checkpoint_relay`) that the new checkpoint extends the current one with `K=6` validly-mined, correctly-linked headers — automated by `btc-checkpoint-relay-worker/`'s poll loop, not a manual admin script. Two things this does NOT close: (1) the genesis anchor itself is still a one-time admin-trusted value — same unavoidable trust-somewhere assumption every SPV/light-client bridge has; (2) `extendCheckpoint` accepts strictly linear extension only — a submission must build on the exact current on-chain checkpoint, with no cumulative-chainwork comparison across competing forks (the BTC-Relay "most work wins" pattern). On signet specifically, where PoW is intentionally cheap, this means a determined actor could still attempt to race the honest chain with their own low-effort but individually-valid-proof fork; full fork-choice resolution is out of scope for v1.
- **Impact**: A compromised admin key can no longer fabricate an arbitrary checkpoint out of thin air (the worst-case blast radius from the old design) — every value after genesis is a provably real chain extension. A deposit transaction may still sit proven but unminted until `btc-checkpoint-relay-worker`'s automatic advances catch the checkpoint up to the deposit's confirming height (typically within one ~10-minute signet block of the worker's own poll interval, not a manual operator action).
- **Roadmap Target**: Cumulative-chainwork comparison across competing checkpoint submissions (full BTC-Relay-style fork choice), which would close the remaining signet-specific race-a-low-effort-fork gap. The manual-operator-step problem this section originally described is already resolved by the permissionless relay above.

## 2. Compliance Attestation Trust Model (Interim `ATTESTER_ROLE`)

- **Limitation**: `ComplianceRegistry.sol` gates `withdraw()` using a centralized `ATTESTER_ROLE` key instead of verifying an on-chain Flare Data Connector (FDC) attestation proof.
- **Impact**: Sanctions screening decisions rely on the attester backend key executing screening rules rather than decentralized FDC consensus rounds.
- **Roadmap Target**: Replace `ATTESTER_ROLE` signature/direct write with verification of Flare Data Connector `JsonApi`/`Web2Json` attestation proofs against independent AML data sources.

## 3. Private Pay Sender Public Caller

- **Limitation**: While `pay()` stealth addresses hide the recipient on-chain via one-time ECIES stealth tags, the transaction calling `StealthAnnouncer.announce()` originates directly from the sender's wallet.
- **Impact**: The sender's address remains visible on-chain even though the recipient is shielded.
- **Roadmap Target**: Route payment announcements through the gasless relayer service to decouple the sender's EOA from the `announce()` event.

## 4. Off-Chain Proving Delegation

- **Limitation**: Server-side proving for `match_orders` and `btc_deposit` requires substantial compute (Noir + Barretenberg `bb.js`), which exceeds lightweight API container resources. Proving is delegated to dedicated worker processes or AWS Lambda workers.
- **Impact**: If proving workers are offline or unconfigured, dark pool matches rest in `awaiting_proof` status.

## 5. Single Operator Testnet Key Model

- **Limitation**: For Coston2 testnet convenience, the backend services (compliance attester, gasless relayer, and dark engine settlement) share a single funded operator key.
- **Impact**: In a production mainnet deployment, each service should use an isolated, minimally-privileged key with strict role separation.

## 6. `ShieldedVault` Admin Is a 2-of-3 Safe, Timelocked (Resolved)

- **Resolved**: `DEFAULT_ADMIN_ROLE` on the live Coston2 `ShieldedVault` (`0xa289AF1069a8ce415434ac329B86578cF9b9c15f`) is held solely by a real, deployed 2-of-3 Safe (`0x740383dB548942f0a280b10345Eaf0e3054D9F8e` — see `contract/deployments/coston2-safe.json`), not an EOA — the deployer key that used to hold this role called `renounceRole` only after verifying the Safe could actually execute a real admin call (`setComplianceRegistry`) end-to-end. This is the SECOND vault this handoff was performed on: an earlier vault (`0x13643D75088cfaB4737E8b6c85813e95bfaB450B`, now stale) got the Safe handoff first, then `ShieldedVault` was redeployed for the timelock/checkpoint-relay redesign (`contract/scripts/redeploy-vault-timelock-checkpoint-relay.ts`) and the exact same grant → verify → renounce sequence was repeated for the new address — confirmed directly against the new contract's on-chain bytecode, which DOES contain the new function selectors (`queueSetTrustedVerifier` etc.), unlike the stale one.
- **Combined effect**: every admin action on the live vault now needs 2 independently-compromised keys (Safe threshold) AND, for `setTrustedVerifier`/`setExternalDepositToken`/checkpoint updates specifically, a public 48h wait after being queued (`AdminActionQueued` event) before it can execute — see item #1 above for the timelock mechanics themselves.
- **Caveat**: Coston2 isn't an officially Safe-supported chain, so this Safe was deployed with real Safe bytecode but not via Safe's deterministic cross-chain CREATE2 factory, and there's no indexed Transaction Service — no app.safe.global dashboard. Signing/execution goes through `contract/scripts/execute-safe-tx.ts` (hash → each owner signs off-chain → anyone submits the aggregated signatures) instead of a UI. See that script's own header comment for the full flow.
- **Still open**: the 3 owner keys are currently a mix of the original deployer key and two freshly-generated Coston2-only keys — real key-custody hygiene (hardware wallets, genuinely separate people/devices for all 3) is an operational choice for whoever holds them going forward, not something code can enforce. Also still open: `executeSetTrustedVerifier`/`executeSetExternalDepositToken` (queued at redeploy time) and the BTC checkpoint genesis bootstrap (`contract/scripts/initialize-btc-checkpoint.ts`) haven't executed yet — BTC deposits stay unavailable on this vault until all three land.

## 7. BTC Payout Custody: 2-of-3 Reserve (Resolved) + No Withdrawal Timeout/Reclaim Path (Open)

- **Resolved**: `BTC_CUSTODIAN_WIF` is no longer the final payout key. It's now purely a deposit-intake hot wallet, periodically swept (`backend/src/btc-withdrawal/sweep.ts`, `BTC_SWEEP_POLL_INTERVAL_MS`) into a real 2-of-3 P2WSH reserve (`backend/src/btc-withdrawal/reserve.ts`) that every real withdrawal now pays out from via PSBT (`backend/src/btc-withdrawal/bitcoin-tx.ts`, `btc-withdrawal.routes.ts`'s `/psbt` routes, `backend/scripts/sign-btc-withdrawal.ts`). This backend process never holds a reserve private key — it can stage an unsigned PSBT but needs 2 of 3 independently-held signers to actually pay anything out, closing the original "one leaked hot-wallet key drains the whole bridge" blast radius down to "one leaked hot-wallet key drains only what's arrived since the last sweep." See `docs/THREAT_MODEL.md`'s custodian/reserve blast-radius sections for the full breakdown.
- **Limitation (open)**: There is still no automatic reclaim or payout timeout. If the custodian hot wallet and/or enough reserve signers become unavailable (not compromised — just offline, unresponsive, or the human coordination to collect 2-of-3 signatures stalls), a real withdrawal that's already nullified on-chain simply sits `pending`/`awaiting_signatures` with no path back to the user and no automatic escalation. This was evaluated against two more complete fixes and both were deliberately deferred: (1) automatic reclaim of a stale nullified withdrawal back to the requester would need to either double-spend-proof the reclaim against a late real payout (a genuine race — the payout and the reclaim can't both be allowed to land) or add a second Noir circuit + custodian bonding to make a late payout unprofitable, and (2) a full "proof of non-payout" liveness circuit is a substantial new circuit that, on its own, doesn't even fully close the double-payment race without bonding on top of it. Both are real future work, not ruled out — just correctly out of scope for this pass, which instead ships the cheap, no-regret half: making a stuck withdrawal loudly, publicly, and quickly visible instead of silently invisible.
- **Impact**: A user whose withdrawal stalls currently has no automatic recourse — only a human operator, once alerted, can act (see below).
- **Mitigation shipped this pass**: `GET /api/btc-withdrawal/solvency`'s `overdueCount`/`oldestOverdueMs` fields and the secret-gated `GET /api/btc-withdrawal/overdue` detail route (`backend/src/btc-withdrawal/overdue.ts`, threshold configurable via `BTC_WITHDRAWAL_OVERDUE_MS`, default 6h) surface any withdrawal stuck past the threshold well before a user has to ask "where's my BTC." See `docs/RUNBOOK_BTC_WITHDRAWAL.md` for the manual response procedure.
- **Roadmap Target**: Either an automatic timeout-based reclaim path (requires closing the double-payment race described above) or reserve-signer bonding, whichever proves more practical once real operational data on how often/why withdrawals stall exists.

## 8. BTC Withdrawal: No Frontend UI, Concurrent-PSBT UTXO Overlap, Checkpoint-Relay Liveness Not Independently Observable

- **No frontend UI for BTC withdrawal destinations yet**: `Shield → Withdraw` (`frontend/src/app/shield/page.tsx`) uses one generic destination-address field for every asset, validated with `isAddress()` (a plain 20-byte EVM address check) and screened via `ComplianceRegistry`. For WrappedBTC specifically, `ShieldedVault.withdraw()` treats that same field's low 160 bits as a Bitcoin P2WPKH `hash160` instead of an EVM address (see `ShieldedVault.sol`'s own NatSpec on `ExternalWithdrawalRequested`) — which happens to satisfy `isAddress()`'s format check since both are 20 bytes, so pasting a raw hash160 hex string into that field technically works, but the UI never explains this, never labels it "Bitcoin address," and runs it through an EVM compliance screen that isn't meaningful for a Bitcoin destination. A real Bitcoin withdrawal today needs a hand-computed hash160, not a pasted `tb1q...` address. This predates this session's backend reserve/PSBT work — flagged now because that work makes BTC withdrawal fulfillment real for the first time, and it surfaced this gap.
- **Concurrent pending BTC withdrawals can select overlapping reserve UTXOs**: `watcher.ts`'s `pollOnce()` processes every `pending` record in one pass, and each call to `bitcoin-tx.ts`'s `buildWithdrawalPsbt` independently re-fetches the reserve's confirmed UTXOs and selects from them — nothing reserves/locks a UTXO across two withdrawals staged in the same pass (or in overlapping passes before either broadcasts). If the reserve doesn't have enough separate UTXOs to cover two withdrawals independently, both can be staged against an overlapping input; whichever finishes collecting 2-of-3 signatures and broadcasts first succeeds, and the other permanently fails to broadcast once its input is already spent — with no automatic recovery (see item #7 above: nothing revisits a stuck `awaiting_signatures` record on its own). Low-probability in practice (the reserve is swept from confirmed hot-wallet inflow and tends to hold few, larger UTXOs, and withdrawal volume during testing is low) but real. Not fixed this pass — closing it needs either an in-process UTXO reservation across a poll pass or serializing withdrawal staging so at most one is `awaiting_signatures`-pending selection at a time.
- **`btc-checkpoint-relay-worker`'s own liveness isn't independently observable**: unlike withdrawal staleness (item #7's `overdueCount`/`oldestOverdueMs`), nothing compares the checkpoint height `GET /api/btc-deposit/checkpoint` reports against the real signet tip and surfaces the gap. If the worker's Lambda schedule is paused, misconfigured, or silently failing every invocation, the only visibility is CloudWatch logs — there's no equivalent of the withdrawal side's public solvency-report signal for "the checkpoint is falling behind, deposits are piling up unminted." A reasonable, cheap follow-up: add a `checkpointLagBlocks` (or similar) field somewhere publicly readable, computed the same way `overdue.ts` computes withdrawal staleness.
